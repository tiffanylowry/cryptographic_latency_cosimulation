# Simulation Toggles and Editing Guide

Every user-facing control point in the co-simulation, organized by layer
(CLI flags → environment variables → config-file keys → GLM directives →
compile-time constants), followed by a task-oriented guide for making common
edits without breaking the generation pipeline's own discipline (generated
files are never hand-edited — see each section for what to edit instead).

All row citations are verified against the current tree, not recalled from
memory — file paths and defaults were re-read while building this table.

---

## 1. Toggle reference table

### 1.1 NS-3 executable CLI flags (`ns3/ns3_cosim_300.cc`, parsed at `main()`)

| Flag | Default | Controls |
|---|---|---|
| `--config=` | `ns3_federate_config_300.json` | Which HELICS federate config the NS-3 side loads |
| `--output=` | `../output/` | Output directory for the CSV log |
| `--crypto-config=` | `crypto/crypto_config_300.txt` | Which crypto config file to load (see §1.3) |
| `--topology-config=` | `topology_config.txt` | Which topology file to load (generated, not a behavioral toggle — see §2.5) |
| `--crypto-enabled=` | *(unset — defer to the config file's own `enabled=`)* | `true`/`false` override, takes precedence over the config file's `enabled=` key |
| `--crypto-selftest` | `false` | Run `ComputeCryptoDelayMs()` self-test and exit — no HELICS/network setup at all |
| `--period=` | `60` (seconds) | Aggregator control-decision cadence (`g_controlPeriodSec`) — independent of the HELICS JSON `period` |
| `--duration=` | `3600` (seconds) | Total simulated duration |
| `--smoothing-alpha=` | sentinel `-1.0` = auto-derive from `--period` (see §1.4) | Curtailment EMA α, overrides the auto-derived value |
| `--sense-buffer=` | sentinel `-1.0` = auto-derive as `min(2.0, period·0.2)` | Sense-relay hybrid-trigger timeout in seconds |

### 1.2 Run-script environment variables (the everyday toggle layer)

These wrap the CLI flags above so day-to-day scenario switching doesn't require editing `run/*.sh` directly.

| Variable | Read by | Default | Controls |
|---|---|---|---|
| `CRYPTO_ENABLED` | all `run_cosim_*.sh` | unset (→ config file default) on `run_cosim_ns3.sh`/`run_cosim_ieee13_300.sh`; `true` on `_fine.sh`/`_realistic.sh` | Maps to `--crypto-enabled=` |
| `CRYPTO_CONFIG` | all `run_cosim_*.sh` | `crypto/crypto_config.txt` (Phase 2/3) or `crypto/crypto_config_300.txt` (Phase 4) | Maps to `--crypto-config=` — **this is how you switch between the "some/production-default" and "worst-case" scenario tags**, by pointing at `crypto_config_300.txt` vs. `crypto_config_300_stress.txt` |
| `CONTROL_PERIOD` | `run_cosim_ieee13_300_fine.sh` (fixed at `1`, not overridable), `run_cosim_ieee13_300_realistic.sh` (`${CONTROL_PERIOD:-30}`) | `1` / `30` | Maps to `--period=` |
| `SIM_DURATION` | `_fine.sh`, `_realistic.sh` | `300` / `3600` | Maps to `--duration=` |
| `SMOOTHING_ALPHA` | `run_cosim_ieee13_300_realistic.sh` only | unset (→ auto-derive) | Maps to `--smoothing-alpha=` if set |

Note: no run script currently exposes a `SENSE_BUFFER` environment variable — testing a non-default sense-buffer means invoking the NS-3 binary directly with `--sense-buffer=`, as done for the tight-buffer sensing-staleness experiment.

### 1.3 `crypto_config_300.txt` keys (hand-rolled `key=value`, generated by `scripts/generate_crypto_config.py` — see §2.2 before hand-editing)

**Global:**

| Key | Example value | Controls |
|---|---|---|
| `enabled` | `false` | Master crypto on/off for this file (overridable per-run by `--crypto-enabled=`) |
| `default_profile` | `ascon-aead128-arm32` | Fallback profile for any node with no role/override match |
| `handshake_enabled` | `false` | One-time ECDHE-style handshake delay, off by default |
| `handshake_profile` | `curve25519-ecdh-m0` |
 Which ECDH profile the handshake (if enabled) uses |
| `rng_seed` | `1` | NS-3 `RngSeedManager::SetSeed()` — **must match across scenario files being compared**, see the paper outline's §3.6/§4.8 on why this is what makes scenario comparisons a controlled experiment |

**Role catalog** (`role.<name>.<key>`, six roles × three keys — one block per role):

| Role | `default_profile` | `tt_budget_ms` | `serial_encrypt` |
|---|---|---|---|
| `protection_relay` | `aes-gcm-artix7` | `3` | `false` |
| `substation_aggregator` | `aes-gcm-artix7` | `20` | `false` |
| `nan_gateway` | `aes-gcm-arm32` | `100` | `false` |
| `nan_concentrator` | `ascon-aead128-arm32` | `100` | `true` |
| `residential_meter` | `ascon-aead128-arm32` | `500` | `true` |
| `legacy_meter` | `none` | `1000` | `true` |

**Per-node overrides** (`node.<id>.<key>`, 383 lines total — one row *pattern*, not enumerated per-node):

| Key pattern | Present for | Controls |
|---|---|---|
| `node.<id>.role=<role>` | every node (aggregator, 7 gateways, 15 concentrators, 300 houses) | Which role-catalog row this node inherits from |
| `node.<id>.profile=<profile\|none>` | 60 houses in the current file (30× `ascon-aead128-avr8`, 30× `ascon-aead128-msp16`) | Explicit override — **always wins over the role default**, giving the mixed-device-class cohort that makes "some crypto" realistic rather than uniform |
| `node.<id>.serial_encrypt=<bool>` | none currently set in `crypto_config_300.txt` (all nodes inherit their role's value) | Per-node override of the role's serialization behavior, if ever needed |

`crypto_config_300_stress.txt` (the "worst case" tag) is the same file with every role's `default_profile` forced to `aes-gcm-arm32` via `sed` — not independently regenerated, so it can drift from `crypto_config_300.txt`'s structure if the latter is regenerated; regenerate both together if you change the role catalog.

### 1.4 GLM `#set` directives (`gridlabd/ieee13_300house_helics*.glm`, written by `scripts/expand_houses.py` — see §2.1)

| Directive | Production value | Realistic value | Controls |
|---|---|---|---|
| `#set randomseed=` | `1` | `1` | GridLAB-D's own `random.normal(...)` draw sequence (house sizes, setpoints, load scaling — see the earlier "what equations" discussion) |
| `#set minimum_timestep=` | `60` | `1` | The **physics** resolution — whole seconds only, `PT_int32` by C++ type; this is the "Layer 3 cadence tag" from the paper outline |
| `#set relax_naming_rules=` | `1` | `1` | GLM parser leniency, unrelated to simulation behavior |
| `default_maximum_voltage_error` (module `powerflow`, not a `#set`) | `0.1` | `0.1` | Convergence tolerance — relaxed from the shipped file's `1e-9`, see §5.1 in the paper outline for why |

### 1.5 HELICS JSON config keys (`gridlabd_helics_config_300*.json`, `ns3_federate_config_300*.json`)

| Key | Production | Realistic | Controls |
|---|---|---|---|
| `period` | `60` | `1` | HELICS exchange granularity — must match the GLM's `minimum_timestep` on the GridLAB-D side |
| `time_delta` | *(absent)* | `0.001` | Sub-period timing resolution, only meaningful once `period` is fine enough to need it |
| `uninterruptible` | `false` | `false` | Must stay `false` — GridLAB-D re-checks subscriptions every timestep only if this is `false` (documented HELICS gotcha) |
| `log_level` | `warning` | `warning` | HELICS core verbosity |
| `terminate_on_error` | `true` | `true` | Fail-fast vs. limp-along on a federate error |

### 1.6 Config-generation script flags (`scripts/generate_rescaled_configs.py` — how a *new* cadence tag gets created)

| Flag | Required? | Controls |
|---|---|---|
| `--glm`, `--gridlabd-config`, `--ns3-config` | required | Source (production) files to transform |
| `--out-glm`, `--out-gridlabd-config`, `--out-ns3-config` | required | Destination paths for the new scenario's generated files |
| `--physics-period` | required (int, seconds) | Drives GLM `minimum_timestep` + both HELICS JSON `period` |
| `--time-delta` | optional (default: `physics_period × 0.001`) | HELICS JSON `time_delta` |
| `--duration-s` | default `300` | Simulated run length for the generated scenario |
| `--control-period-hint` | optional | Cosmetic — informs the script's own console output, not consumed by the simulators |

## 2. Editing guide — how to change things without breaking the pipeline

The project's one hard rule, repeated throughout `CLAUDE.md`: **generated files are never hand-edited.** If a file's header says "Generated by `scripts/X.py` — do not hand-edit," change the script or its inputs and regenerate, don't patch the output. This guide is organized around that rule — for each kind of change, it says which script/config to touch and which files to leave alone.

### 2.1 "I want to run an existing scenario"

No editing needed — pick the right environment variables (§1.2) and run script:

```bash
# No crypto, production cadence
CRYPTO_ENABLED=false bash run/run_cosim_ieee13_300.sh

# Production-default crypto (mixed device classes), production cadence
CRYPTO_ENABLED=true CRYPTO_CONFIG=crypto/crypto_config_300.txt bash run/run_cosim_ieee13_300.sh

# Worst-case crypto, decoupled/realistic cadence
CRYPTO_ENABLED=true CRYPTO_CONFIG=crypto/crypto_config_300_stress.txt \
    bash run/run_cosim_ieee13_300_realistic.sh
```

### 2.2 "I want to change a device's crypto profile" (e.g., test a different cipher on concentrators)

Edit `gridlabd/topology_manifest.json`'s role/device-class assignment and rerun `scripts/generate_crypto_config.py`, **not** `crypto_config_300.txt` directly — the file's own header says why. If you only need a one-off test (not a reproducible scenario), a direct edit to `crypto_config_300.txt`'s `role.<name>.default_profile=` line is lower-risk than editing per-node lines, since there are only 6 role lines vs. 383 node lines to keep consistent; just don't commit that edit as if it were regenerated.

To add a new profile entirely (a cipher not yet in the benchmark table): add a row to `ns3/crypto/crypto_benchmarks.h`'s `CRYPTO_PROFILES[]` array with a real citation (see `ns3/crypto/README.md`'s existing table-by-table provenance pattern), not a guessed number.

### 2.3 "I want a new cadence scenario" (a control period / physics resolution combination that doesn't exist yet)

Use `scripts/generate_rescaled_configs.py` (§1.6) against the production files — this is exactly how the `_realistic` and `_fine` scenarios were created, and is the pattern to follow for a new one. Then write a matching `run/run_cosim_ieee13_300_<name>.sh` by copying `run_cosim_ieee13_300_realistic.sh`'s structure (env-var defaults, the three-process broker/GridLAB-D/NS-3 launch sequence).

### 2.4 "I want to change curtailment behavior" (thresholds, smoothing)

- `--smoothing-alpha=` (§1.1) is runtime-toggleable, no rebuild — use this for smoothing experiments.
- `VOLTAGE_LOW`/`VOLTAGE_CRITICAL` (currently 118V/116V) and `BASELINE_PERIOD_SEC`/`BASELINE_SMOOTHING_ALPHA` (the 60s/0.3 pair `ComputeAutoSmoothingAlpha()` derives from) are `static const double` in `ns3_cosim_300.cc` — **compile-time constants, not runtime toggles**. Changing them requires editing the source and rebuilding (`bash ns3/build_ns3_federate.sh`) before the change takes effect. If you're testing the IEEE 1547/ANSI C84.1-grounded thresholds discussed earlier in this conversation, this is the edit point.

### 2.5 "I want to change the network topology or link speeds"

`ns3/topology_config.txt` is generated (from `topology_manifest.json` via `scripts/generate_ns3_topology_config.py`) and describes node/link *structure* (which concentrator belongs to which gateway, HELICS index mappings) — regenerate, don't hand-edit, if the underlying feeder topology changes. Link *parameters* (10Mbps/5ms P2P, 2Mbps/3ms CSMA) are `static` calls to `SetDeviceAttribute`/`SetChannelAttribute` in `ns3/cosim_topology.h`'s `BuildCosimTopology()` — compile-time constants, same rebuild requirement as §2.4. This is the edit point for the IEEE 802.15.4g/Wi-SUN-grounded NAN throughput correction discussed earlier.

### 2.6 "I want to change the grid model itself" (feeder topology, house count, load profiles)

Don't. `gridlabd/reference/IEEE_13_Node_With_Houses.glm` is explicitly read-only — GridLAB-D's own shipped, solver-validated reference, never edited (this is the project's core anti-transcription-risk discipline, stated repeatedly throughout `CLAUDE.md`). All derived changes go through `scripts/expand_houses.py` acting on that reference, producing `gridlabd/ieee13_300house_helics*.glm` as output. If a real change to house count/topology is genuinely needed, it means changing GridLAB-D's *own* shipped example (out of this project's scope) or building a new, separately-justified synthetic model — not editing the generated `.glm` files directly.

### 2.7 "I made a source change (`.cc`/`.h`) — how do I actually test it?"

1. Edit on the Windows-side project (`/mnt/c/REU 2026/Co-Simulator/`).
2. Sync to the WSL working copy — builds/runs must happen inside WSL2's filesystem, not `/mnt/c` (documented as too slow via 9P):
   ```bash
   rsync -a --delete "/mnt/c/REU 2026/Co-Simulator"/. ~/co-sim-project/
   ```
3. Rebuild: `cd ~/co-sim-project/ns3 && bash build_ns3_federate.sh`
4. Run whichever scenario script exercises the change.
5. If the change should persist, edit stays on the Windows side (the source of truth) — the WSL copy is a disposable build/run target, not where edits should originate.

### 2.8 "I want to patch installed third-party source" (GridLAB-D, NS-3, or the helics-ns3 contrib module)

Follow the project's own established precedent (`install/05_install_helics_ns3.sh`'s 8 documented patches) rather than editing the install in place with no record: make the change in the installed source tree (`~/cosim/src/...`, which is a git repo pinned to a specific tag — use `git diff`/`git status` to keep the change reviewable), save the diff as a tracked `.patch` file in the project, write a small apply-and-rebuild script, and confirm via `git status` that the source tree is clean again if the patch is later reverted. Never edit the actual system install (`/usr/local/lib/*.so`) directly — test patched builds via a `GLPATH` (GridLAB-D) or equivalent override rather than overwriting the installed module.
